# บันทึกช่วยจำ: งานที่ต้องทำภายหลัง

## 1. คู่มือเชื่อมต่อ HIS สำหรับฝ่าย IT ของโรงพยาบาล

**ทำเมื่อ:** ได้งานกับโรงพยาบาลแล้ว (รู้ว่าใช้ HIS ตัวไหน และฝ่าย IT เปิดให้เชื่อมแบบไหน)

**ระบบพร้อมแล้ว:** API ขาเข้า `/api/his/v1/…` ทำไว้แล้ว (`app/his.py`, migration 017) และรายละเอียดทุกช่องดูได้ที่ `/api/docs` หัวข้อ HIS

**ควรมีในคู่มือ:**
- **ภาพรวม:**
  - HIS เป็นฝ่ายเรียกเข้ามาด้วย HTTPS ขาออก ไม่ต้องเปิด port ขาเข้าที่โรงพยาบาล
  - ต้องอนุญาตโดเมนของ ORchestraAI ใน firewall
- **API key:** วิธีขอ key จาก admin, การเก็บ key ให้ปลอดภัย, การส่งใน header `Authorization: Bearer <key>` และการยกเลิกหรือเปลี่ยน key
- **ช่องข้อมูลใบขอผ่าตัด:**
  - ความหมายของแต่ละช่อง และช่องที่บังคับ
  - ตัวอย่าง JSON ทั้งแบบสร้าง/แก้ไข และแบบยกเลิก
  - ตัวอย่างคำสั่ง curl
- **กติกา:**
  - `his_ref` ต้องไม่ซ้ำ และส่งซ้ำได้โดยไม่เกิดรายการซ้ำ
  - batch ส่งได้ครั้งละไม่เกิน 200 รายการ
  - จำกัด 300 ครั้งต่อนาทีต่อ key
- **การตีความผลลัพธ์:**
  - สถานะ: APPLIED / UNCHANGED / NEEDS_MAPPING / NEEDS_ACTION / REJECTED
  - รหัส HTTP: 200 / 401 / 403 / 404 / 422 / 429 / 503
  - ควรลองส่งซ้ำเมื่อไหร่
- **ตารางจับคู่รหัส:**
  - รหัสแพทย์ของ HIS ↔ รหัสพนักงาน และรหัสหัตถการ ↔ ICD-9-CM
  - ขอไฟล์รหัสจาก IT มาจับคู่ล่วงหน้า
- **การอ่านกลับ:** สถานะรายใบ และตารางผ่าตัดรายวัน ซึ่งมี HN (ต้องเก็บรักษาแบบข้อมูลผู้ป่วย)
- **ขั้นตอนทดสอบร่วมกัน:** ping → ส่งใบขอทดสอบ → จับคู่รหัส → อ่านสถานะ → ยกเลิก
- **PDPA:**
  - ส่งเฉพาะข้อมูลที่จำเป็นต่อการนัด
  - ทำข้อตกลงการประมวลผลข้อมูลกับโรงพยาบาล
  - ระยะเวลาเก็บข้อมูลในกล่องรับข้อมูล (30 วัน)
- **ถ้าโรงพยาบาลมี API ให้เราเรียกได้ (เช่น ค้นชื่อจาก HN):** เขียนตัวเชื่อมที่ส่งเข้า `His.receive()` เพิ่ม 1 ไฟล์

## 2. คู่มือสำหรับทีม Dev ของเรา (รวม workflow)

**ควรมี:**
- **โครงสร้างระบบ:**
  - `orchestra_engine/` (Agent และ CP-SAT)
  - `app/` (FastAPI, `DatabaseStore` / `ScheduleStore`, หน้าเว็บใน `app/static/`)
  - `supabase/migrations/`
- **ตั้งเครื่องสำหรับพัฒนา:**
  - Python 3.12 และ virtualenv
  - PostgreSQL ในเครื่องสำหรับเทสต์ (`TEST_DATABASE_URL`)
  - โหมดข้อมูลจำลอง (ไม่ตั้ง `DATABASE_URL`) และโหมด Supabase
- **Workflow ของงานแต่ละชิ้น:**
  1. แตก branch จาก main
  2. เขียนโค้ดและเทสต์ (pytest + pyflakes)
  3. ลองในเบราว์เซอร์ (Playwright)
  4. commit แล้วเปิด PR
  5. รอ GitHub Actions ผ่าน แล้ว merge
  6. Render deploy อัตโนมัติ
  7. ถ้ามีไฟล์ SQL ใหม่ ให้รันจากหน้า ⚙ สถานะระบบ
- **กติกา migration:**
  - ตั้งชื่อไฟล์ตามวันที่และรันซ้ำได้ (`IF NOT EXISTS`)
  - ระบบต้องทำงานได้ก่อนรันไฟล์ (ตรวจตารางหรือคอลัมน์ตอนรัน)
  - เพิ่มชื่อภาษาไทยใน `system_status.TITLES`
  - มีเทสต์ "works before migration"
- **กติกาโค้ด:**
  - ข้อความที่ผู้ใช้เห็นเป็นภาษาไทย (มีเทสต์กันภาษาอังกฤษ)
  - แจ้งเตือนและบันทึกกิจกรรมห้ามมี HN หรือชื่อผู้ป่วย
  - ข้อความอิสระต้องผ่าน `mask_identifiers`
  - ปุ่มที่คู่มือ `/help` อ้างถึงต้องมีจริง (`tests/test_help.py`)
- **ความปลอดภัย:**
  - CSRF (POST ต้องเป็น JSON)
  - สิทธิ์ตามบทบาท (`app/auth.py`)
  - บันทึกการเข้าถึงข้อมูลผู้ป่วย (`app/privacy.py`)
  - API key ของ HIS
- **การปล่อยเวอร์ชันและดูแลระบบ:**
  - ดูหน้า ⚙ สถานะระบบ
  - สำรองข้อมูลทุกสัปดาห์
  - ดูข้อผิดพลาดและเรื่องที่ผู้ใช้แจ้ง
  - ค่าตั้งใน Render Environment
