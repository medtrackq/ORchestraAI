# ข้อกำหนดการเชื่อมต่อระบบโรงพยาบาล (HIS) กับ ORchestraAI

เอกสารนี้สำหรับฝ่าย IT ของโรงพยาบาลและผู้ดูแลระบบ ORchestraAI · ฟังก์ชันเสริม: ระบบทำงานครบโดยไม่ต้องเชื่อม และไม่มีผลใด ๆ จนกว่าผู้ดูแลจะสร้าง API key หรือตั้งค่าการดึงข้อมูล

| ส่วน | ข้อมูล | ทิศทาง | รูปแบบ |
|---|---|---|---|
| **A. ข้อมูลหลัก** | บุคลากรห้องผ่าตัดและตารางเวร · ห้องผ่าตัด · เครื่องมือ | HIS → ORchestraAI (HIS ส่งเข้ามา หรือ ORchestraAI ไปดึง) | **HL7 FHIR R4** (JSON) |
| **B. ใบขอผ่าตัด** | ใบขอผ่าตัดเข้ารายการรอผ่าตัด · สถานะคำขอ · ตารางผ่าตัดรายวัน | HIS → ORchestraAI และ HIS อ่านกลับ | JSON ของ ORchestraAI (`/api/docs` หัวข้อ HIS) |
| **C. เวลาแต่ละขั้นจากอุปกรณ์** | ผู้ป่วยเข้า/ออกห้อง ลงมีด เย็บแผลเสร็จ จากกล้อง AI, RFID หรือระบบในห้องผ่าตัด | อุปกรณ์ → ORchestraAI | JSON (`POST /api/his/v1/milestones`) |

ที่อยู่ระบบ (ตัวอย่าง): `https://orchestra-ai-production.up.railway.app` · ทุกช่องทางใช้ HTTPS เท่านั้น

## 1. สถาปัตยกรรม

```
 ┌──────────────────────────────── HIS โรงพยาบาล ─────────────────────────────────┐
 │  FHIR R4 server   หรือ   HL7 v2 / ฐานข้อมูล → interface engine (เช่น Mirth Connect) │
 └──────┬──────────────────────────────▲───────────────────────────────┬───────────┘
   (1) push                             │ (2) pull                      │ (3) ใบขอผ่าตัด
   POST /api/his/v1/fhir                │ GET [base]/Location …         │ POST /api/his/v1/surgery-requests
   Authorization: Bearer orc_…          │ Authorization: Bearer <token> │ GET  /api/his/v1/schedule
        ▼                               │                               ▼
 ┌──────────────────────────────────── ORchestraAI ───────────────────────────────────────┐
 │  his_fhir.MasterData.run  (FHIR → ข้อมูลหลัก · ทดลองได้ · ตรวจเหมือนนำเข้า Excel)          │
 │     operating_rooms / staff / equipment_units / staff_schedules  (managed_by = 'his')   │
 │     his_external_refs (id ของ HIS ↔ record)   his_sync_runs (ประวัติทุกครั้ง)            │
 │  his.His.receive  (ใบขอผ่าตัด → รายการรอผ่าตัด · รอจับคู่รหัส)                            │
 └──────────────────────────────────────────────────────────────────────────────────────────┘
```

- **มาตรฐานเดียวสำหรับข้อมูลหลัก: HL7 FHIR R4** · HIS ที่ยังไม่มี FHIR (ส่ง HL7 v2 หรือมีแค่ฐานข้อมูล) ให้ใช้ interface engine แปลงเป็น FHIR แล้วส่งเข้ามา ORchestraAI จึงไม่ต้องมีตัวแปลงเฉพาะยี่ห้อ HIS
- **รับข้อมูลหลักได้ 3 ทาง:** (1) HIS ส่งเข้ามา (2) ORchestraAI ไปดึงจาก FHIR server ของ HIS เป็นรอบ (3) ผู้ดูแลนำเข้าไฟล์ Bundle เอง (ใช้ทดลองก่อนเปิดจริง)
- **ทุกครั้งทดลองก่อนได้ (dry run):** ระบบทำงานจริงทุกขั้นแล้วยกเลิกทั้งหมด ผลทดลองจึงตรงกับการนำเข้าจริง
- **HIS อยู่ในเครือข่ายภายใน:** ใช้ทาง (1) หรือ (3) ได้โดยไม่ต้องเปิด port ขาเข้าที่โรงพยาบาล (HIS เรียก HTTPS ขาออกมาเอง) · ทาง (2) ใช้เมื่อ FHIR server ของโรงพยาบาลเปิดให้เรียกจากภายนอกได้ (หรือผ่าน VPN)

## A. ข้อมูลหลัก (HL7 FHIR R4)

### A1. HIS ส่งเข้ามา

```
POST /api/his/v1/fhir[?dry_run=true]
Authorization: Bearer orc_…            ← API key ที่มีสิทธิ์ "ส่งข้อมูลหลัก (FHIR)" (masterdata:write)
Content-Type: application/fhir+json    ← หรือ application/json

{ "resourceType": "Bundle", "type": "collection", "entry": [ { "resource": { … } }, … ] }
```

- รับ Bundle (ทุกชนิด: collection, batch, transaction, searchset), resource เดี่ยว หรือ array · ครั้งละไม่เกิน **20,000 resource / 20 MB**
- resource ที่ใช้: `Location`, `Practitioner`, `PractitionerRole`, `Device`, `Schedule`, `Slot` · ชนิดอื่นไม่ใช้ (ไม่ error) · **ไม่ต้องส่งข้อมูลผู้ป่วย**
- ตอบกลับเป็น `OperationOutcome` พร้อมสถิติ:

```json
{
  "resourceType": "OperationOutcome",
  "status": "partial", "dry_run": false, "committed": true, "run_id": 42,
  "issue": [
    { "severity": "information", "code": "informational",
      "diagnostics": "room: new 1, changed 1, unchanged 2, linked 2, skipped 3, failed 0; staff: …; roster: days changed 12, …" },
    { "severity": "error", "code": "processing", "expression": ["Location/loc-or7"],
      "diagnostics": "รหัสห้อง 'OR 7 big' ใช้ไม่ได้ (1-20 ตัว A-Z 0-9 - _ . ไม่มีช่องว่าง) …" }
  ],
  "stats": { "room": { "new": 1, "changed": 1, "unchanged": 2, "linked": 2, "skipped": 3, "failed": 0 },
             "staff": { … }, "equipment": { …, "retired": 1 },
             "roster": { "days": 12, "unchanged": 2, "added": 12, "removed": 0, "adopted": 0, "skipped": 0, "failed": 0 } }
}
```

| HTTP | ความหมาย | ควรทำ |
|---|---|---|
| 200 | `status` = `success` (ทุกรายการผ่าน) หรือ `partial` (บางรายการไม่ผ่าน รายการอื่นบันทึกแล้ว) | ดู `issue` ที่ severity `error` แก้แล้วส่งใหม่ (ส่งซ้ำได้ ไม่เกิดข้อมูลซ้ำ) |
| 422 | `status` = `failed` ไม่มีรายการใดผ่าน | ดู `issue` |
| 400 | ไม่ใช่ JSON / เกินจำนวน / มีการรับข้อมูลอีกชุดกำลังทำงาน | แก้แล้วส่งใหม่ · กรณีกำลังทำงาน ลองใหม่ในอีกครู่ |
| 401 / 403 | ไม่มี key / key ผิดหรือถูกยกเลิก / key ไม่มีสิทธิ์ `masterdata:write` | ขอ key ใหม่จากผู้ดูแล |
| 413 | ข้อมูลเกิน 20 MB | แบ่งส่ง (เช่น ตารางเวรทีละ 1–2 สัปดาห์) |
| 429 | key ผิดหลายครั้ง หรือเรียกเกิน 300 ครั้ง/นาที | รอ 1 นาที |
| 503 | ฐานข้อมูลยังไม่ได้รัน SQL ไฟล์ 019 หรือเชื่อมต่อไม่ได้ | แจ้งผู้ดูแล แล้วส่งใหม่ภายหลัง |

ตัวอย่าง (ทดลองก่อน):

```bash
curl -X POST "https://<ที่อยู่ระบบ>/api/his/v1/fhir?dry_run=true" -H "Authorization: Bearer $ORC_KEY" -H "Content-Type: application/fhir+json" --data-binary @sample-bundle.json
```

ไฟล์ตัวอย่างครบทุกชนิด: [`docs/integration/sample-bundle.json`](integration/sample-bundle.json) (สร้างใหม่ให้เป็นวันที่ข้างหน้าได้ด้วย `python tests/fhir_sample.py 2026-12-01`)

### A2. การจับคู่ FHIR → ข้อมูลใน ORchestraAI

รับเฉพาะของห้องผ่าตัด: Location ที่ไม่ใช่ห้องผ่าตัด, บุคลากรที่ไม่มีบทบาทห้องผ่าตัด และอุปกรณ์ชนิดอื่น **นับเป็น "ข้าม"** (ไม่ใช่ error) จึงส่งข้อมูลทั้งโรงพยาบาลมาได้

| FHIR R4 | ใน ORchestraAI | จับคู่กับ record เดิมด้วย | ช่องที่ใช้ |
|---|---|---|---|
| `Location` ที่ `type` มีรหัสในตาราง "ประเภทห้อง" | ห้องผ่าตัด | รหัสห้อง | `identifier` (system ที่ตั้งไว้ ไม่ตั้ง = ตัวแรก) → `alias` → `name` เป็นรหัสห้อง (1-20 ตัว A-Z 0-9 - _ .) · `status` active = ใช้งานได้, suspended = ซ่อมบำรุง, inactive = ปิดใช้งาน · `operationalStatus` C = ปิดใช้งาน · `type` → ประเภทห้อง (เฉพาะห้องใหม่) |
| `Location` อื่น (หอผู้ป่วย ชั้น CSSD) | ข้าม · จำชื่อไว้ | – | ใช้เป็นชื่อที่เก็บของเครื่องมือที่อ้าง `Device.location` |
| `Location` physicalType `bd` (เตียง) | ข้าม (ยังไม่รับ) | – | – |
| `Practitioner` + `PractitionerRole` | บุคลากร | รหัสพนักงาน | รหัสพนักงาน = `identifier` (system รหัสพนักงาน หรือ type `EI`) → เลขใบอนุญาต (type `PRN`/`LN`/`MD`) → `HIS-<id>` · ชื่อ = `name.text` หรือ `prefix`+`given` `family` · บทบาท = รหัสใน `PractitionerRole.code` / `specialty` หรือ `Practitioner.qualification.code` ตามตาราง "บทบาท" (ไม่มี = ข้าม) · `active` · ความเชี่ยวชาญ = `PractitionerRole.specialty` (เฉพาะคนใหม่) · บทบาทที่ `active: false` ไม่นับ |
| `Device` ที่ `type` ตรงชนิดเครื่องมือ | เครื่องมือรายชิ้น | หมายเลขเครื่อง | หมายเลข = `identifier` (system เลขครุภัณฑ์ ไม่ตั้ง = ตัวแรก) → `serialNumber` · ชนิด = `type` ตามตาราง "ชนิดเครื่องมือ" หรือรหัส/ชื่อที่ตรงกับชื่อชนิดในระบบ (ไม่ตรง = ข้าม) · `status` inactive / entered-in-error = **ปลดระวาง** (ไม่ถูกใช้ในการจองอีก) active = กลับมาใช้ · `location` → ที่เก็บ (เฉพาะเครื่องใหม่) |
| `Schedule` | ตารางเวรของ 1 คน | `actor` → Practitioner (หรือ PractitionerRole) ที่ส่งมาด้วยหรือเคยส่ง หรือ `actor.identifier` = รหัสพนักงาน | `planningHorizon` = ช่วงวันที่ HIS รับผิดชอบตารางเวร (ไม่เกิน 93 วัน) |
| `Slot` | 1 เวร | `schedule` | `start` / `end` (ISO 8601 พร้อม timezone ไม่เกิน 36 ชม.) · ประเภทเวรจาก `serviceType` / `appointmentType` / `serviceCategory` ตามตาราง "ประเภทเวร" ไม่มีรหัส: `free` = เวรปกติ, `busy-unavailable` = ลา (`comment` = ประเภทการลา) · `OFF` และ `entered-in-error` = ไม่ใช่เวร · วันของเวร = วันที่เริ่ม (เวลาไทย) |

**ตารางจับคู่รหัส** (ผู้ดูแลตั้งที่หน้า ข้อมูลโรงพยาบาล → เชื่อมต่อ HIS → จับคู่รหัสของ HIS · ค่าเริ่มต้นในวงเล็บ)

| ตาราง | จากรหัส | เป็น |
|---|---|---|
| ประเภทห้อง | `Location.type` (`OR`, `OR-HYBRID`, `OR-NEG`) | `STANDARD` / `HYBRID` / `NEGATIVE_PRESSURE` · รหัสที่ไม่อยู่ในตาราง = ไม่ใช่ห้องผ่าตัด |
| บทบาท | `PractitionerRole.code`, `specialty`, `qualification.code` (`SURGEON`, `ANESTHESIOLOGIST`, `SCRUB_NURSE`, `CIRCULATING_NURSE`) | บทบาทเดียวกัน · ใส่รหัสของโรงพยาบาลเพิ่มได้ เช่น `0055 = ANESTHESIOLOGIST` |
| ชนิดเครื่องมือ | `Device.type` (`system\|code` หรือ `code`) | ชื่อชนิดเครื่องมือในระบบ (ต้องสร้างชนิดในแท็บเครื่องมือก่อน เพราะมีเวลาอบฆ่าเชื้อของ CSSD) |
| ประเภทเวร | `Slot.serviceType` ฯลฯ (`REGULAR`, `ON_CALL`, `ONCALL`, `LEAVE`, `OFF`) | `REGULAR` / `ON_CALL` / `LEAVE` / `OFF` |
| identifier system | – | ระบุว่า identifier ไหนคือรหัสพนักงาน เลขใบอนุญาต เลขครุภัณฑ์ รหัสห้อง (ไม่บังคับ) |

### A3. เจ้าของข้อมูล (field ownership)

record ที่มาจาก HIS มีป้าย **HIS** ในหน้าเว็บ ฟิลด์ที่ HIS เป็นเจ้าของ **แก้ใน ORchestraAI ไม่ได้** ทั้งในฟอร์มและการนำเข้า Excel (ตอบ "มาจาก HIS: แก้ … ที่ HIS") ส่วนข้อมูลการทำงานของห้องผ่าตัดยังแก้ได้ตามปกติ

| ข้อมูล | HIS เป็นเจ้าของ | ทีมห้องผ่าตัดเป็นเจ้าของ |
|---|---|---|
| ห้องผ่าตัด | รหัสห้อง · เปิด/ปิดใช้งาน | ประเภท (ค่าเริ่มจาก HIS) · ความสามารถของห้อง · เวลาทำความสะอาด · เวลารับเคส elective · ปิดห้องชั่วคราว · บล็อกห้อง |
| บุคลากร | รหัสพนักงาน · ชื่อ · บทบาท · ใช้งาน | ความเชี่ยวชาญ (ค่าเริ่มจาก HIS) · ทักษะ · เกณฑ์ชั่วโมงทำงาน/พัก |
| เครื่องมือ | หมายเลขครุภัณฑ์ · ชนิด · ปลดระวาง | สถานะ CSSD · ที่อยู่ตอนนี้ (ค่าเริ่มจาก HIS) · นัดซ่อมบำรุง |
| ตารางเวร | เวรที่ HIS ส่งมา | เวรที่เพิ่มใน ORchestraAI (เช่น on-call เพิ่มเฉพาะกิจ) |

### A4. กันข้อมูลซ้ำ และการส่งซ้ำ

1. **จับคู่ด้วยรหัส:** ห้อง = รหัสห้อง, บุคลากร = รหัสพนักงาน, เครื่องมือ = หมายเลขเครื่อง (ไม่สนตัวพิมพ์เล็ก/ใหญ่) → ส่งซ้ำกี่ครั้งก็อัปเดต record เดิม
2. **ผูกกับข้อมูลที่กรอกไว้ก่อน (linked):** ห้อง/คน/เครื่องที่กรอกเองหรือนำเข้า Excel ไว้ก่อนเชื่อมต่อ ถ้ารหัสตรงกันจะกลายเป็นของ HIS แทนการสร้างใหม่
3. **ไม่เปลี่ยนไม่เขียน:** ข้อมูลเหมือนเดิม = "ไม่เปลี่ยน" ไม่บันทึกและไม่เตือนซ้ำ
4. `his_external_refs` จำว่า `Practitioner/123` คือใคร `Location/abc` คือห้องไหน จึงส่ง `Schedule` หรือ `Device` ที่อ้างถึง resource ที่ส่งไปแล้วในครั้งก่อนได้
5. รายการที่ผิดพลาดล้มเฉพาะรายการนั้นพร้อมเหตุผล รายการอื่นบันทึกได้ตามปกติ

### A5. ตารางเวร

- **ต่อคนต่อวันที่ส่งมา** (วันของ Slot ทุกวัน และ**ทุกวันใน `planningHorizon`**) เวรที่ HIS ส่งคือเวรของ HIS ทั้งหมดในวันนั้น:
  - เวรที่ HIS เคยส่งแต่ไม่ส่งแล้ว → ลบ (เช่น ยกเลิกเวร: ส่ง Schedule ที่ planningHorizon ครอบวันนั้นโดยไม่มี Slot)
  - เวรที่ตรงกับเวรที่กรอกไว้ใน ORchestraAI ทุกอย่าง → รับเป็นของ HIS (ไม่เกิดซ้ำ)
  - เวรที่เพิ่มใน ORchestraAI → คงไว้
- วันที่รับได้: ย้อนหลัง 62 วันถึงข้างหน้า 400 วัน · `planningHorizon` ครั้งละไม่เกิน 93 วัน
- เวรจาก HIS ลบหรือแก้ในหน้าตารางเวรไม่ได้ และไฟล์ Excel ตารางเวรแก้วันที่มีเวรจาก HIS ไม่ได้
- เมื่อตารางเวรเปลี่ยนจนเคสที่จองไว้ผิดเงื่อนไข (คนไม่อยู่เวร เกินชั่วโมง) ระบบแสดงรายการวันที่ได้รับผลกระทบให้ผู้จัดตาราง

### A6. ORchestraAI ไปดึงจาก FHIR server ของ HIS (pull)

ผู้ดูแลตั้งค่า: ที่อยู่ FHIR server (`https://…`) · ชื่อตัวแปร token (ขึ้นต้นด้วย `HIS_` เช่น `HIS_TOKEN`) แล้วใส่ token จริงที่ **Railway → Variables** (ระบบไม่เก็บ token ในฐานข้อมูล) · ดึงอัตโนมัติทุก N ชั่วโมง (0 = กดเอง) · จำนวนวันของตารางเวร

คำขอที่ ORchestraAI ส่ง (ตามลำดับ, `Authorization: Bearer <token>`, `Accept: application/fhir+json`):

```
GET [base]/metadata                                   ← ปุ่ม "ทดสอบการเชื่อมต่อ"
GET [base]/Location?_count=200[&_lastUpdated=gt<ครั้งก่อน>]
GET [base]/Practitioner?…    GET [base]/PractitionerRole?…    GET [base]/Device?…
GET [base]/Schedule?_count=200                        ← ทุกครั้ง (ช่วงวันของตารางเวร)
GET [base]/Slot?_count=200&start=ge<เมื่อวาน>&start=lt<อีก N วัน>
```

- ตามลิงก์ `next` ของ Bundle ได้เฉพาะเซิร์ฟเวอร์เดียวกับที่ตั้งไว้ ไม่ตาม redirect · timeout 30 วินาที · หน้าละไม่เกิน 25 MB
- `_lastUpdated` ใช้เวลาล่าสุดที่ได้ (`meta.lastUpdated`) ของครั้งก่อนที่สำเร็จ จึงดึงเฉพาะที่เปลี่ยน · ตารางเวรดึงทั้งช่วงทุกครั้ง (ทุกวันในช่วงคือเวรของ HIS)
- ดึงอัตโนมัติ: ทำครั้งเดียวต่อรอบแม้มีหลายเซิร์ฟเวอร์ · ผลอยู่ในประวัติการรับข้อมูล และข้อผิดพลาดขึ้นหน้า ⚙ สถานะระบบ

### A7. ความปลอดภัยและ PDPA

- API key สุ่ม 256 บิต เก็บเฉพาะ hash · แยกสิทธิ์ (`masterdata:write` ไม่อ่านหรือส่งใบขอผ่าตัดได้) · จำกัด 300 ครั้ง/นาที/key และจำกัด key ผิดต่อ IP · ยกเลิก key ได้ทันทีที่หน้าเชื่อมต่อ HIS
- ข้อมูลหลักไม่มีข้อมูลผู้ป่วย · เก็บเฉพาะที่ห้องผ่าตัดใช้: ไม่เก็บเลขใบอนุญาต (ใช้เป็นรหัสพนักงานเมื่อไม่มีรหัสอื่นเท่านั้น) เบอร์โทร หรือที่อยู่ของบุคลากร
- ทุกการรับข้อมูลบันทึกใน `his_sync_runs` (ใคร ช่องทางไหน ผลอย่างไร) และประวัติกิจกรรม
- ควรทำข้อตกลงการประมวลผลข้อมูล (DPA) กับฝ่าย IT โรงพยาบาลก่อนเปิดใช้งานจริง

## B. ใบขอผ่าตัด (JSON)

API key สิทธิ์ `requests:write` (ส่ง) และ `schedule:read` (อ่าน) · รายละเอียดทุกช่องและลองเรียกได้ที่ `/api/docs` หัวข้อ HIS (ต้องเข้าระบบ)

| คำขอ | ใช้ทำอะไร |
|---|---|
| `GET /api/his/v1/ping` | ทดสอบ key |
| `POST /api/his/v1/surgery-requests` | สร้าง แก้ไข หรือยกเลิก (`"action": "cancel"`) ใบขอผ่าตัด 1 ใบ · ส่งซ้ำด้วย `his_ref` เดิมได้ |
| `POST /api/his/v1/surgery-requests/batch` | ครั้งละไม่เกิน 200 ใบ (แต่ละใบผลแยกกัน) |
| `GET /api/his/v1/surgery-requests/{his_ref}` | สถานะ: รอ · จองแล้ว (วัน เวลา ห้อง) · ผ่าตัดแล้ว · ยกเลิก |
| `GET /api/his/v1/schedule?date=YYYY-MM-DD` | ตารางผ่าตัดของวัน (มี HN: เก็บรักษาแบบข้อมูลผู้ป่วย) |

```json
{ "his_ref": "OR-2026-000123", "hn": "6512345", "patient_name": "…",
  "surgeon_code": "D-2001", "procedure_code": "51.23", "urgency": "ELECTIVE",
  "requested_date": "2026-12-03", "due_date": "2026-12-10" }
```

- ช่องที่ใช้: `his_ref` (บังคับ ไม่ซ้ำ) · `action` (`upsert` / `cancel`) · `hn` · `patient_name` · `surgeon_code` / `surgeon_name` · `procedure_code` (ICD-9-CM หรือรหัสของ HIS) / `procedure_name` · `urgency` (`ELECTIVE` / `URGENT` / `EMERGENCY`) · `duration_mins` (15–720 ไม่ส่ง = ใช้ preference card) · `requested_date` · `due_date` · `requires_icu` · `airborne`
- ผลรายใบ: `APPLIED` บันทึกแล้ว · `UNCHANGED` ไม่มีอะไรเปลี่ยน · `NEEDS_MAPPING` รอผู้ดูแลจับคู่รหัสแพทย์/หัตถการ (ไม่ต้องส่งใหม่ ระบบทำต่อเองเมื่อจับคู่) · `NEEDS_ACTION` ต้องดำเนินการในระบบ (เช่น เคสจองแล้วแต่ HIS ขอเปลี่ยน) · `REJECTED` ข้อมูลไม่ถูกต้อง · ใน batch `ERROR` = ระบบขัดข้อง ส่งใบนั้นใหม่ภายหลัง
- จำกัด 300 ครั้ง/นาที และ 1,200 ใบ/นาที ต่อ key · ข้อมูลต่อครั้งไม่เกิน 1 MB · ข้อความในกล่องรับข้อมูลที่มี HN ถูกล้างเมื่อบันทึกแล้ว และหลัง 30 วันถ้าไม่เคยบันทึกได้
- **แนะนำ:** ส่งบุคลากรผ่านส่วน A ก่อน แล้ว `surgeon_code` ของใบขอผ่าตัดจะตรงกับรหัสพนักงานทันที ไม่ต้องจับคู่รหัสแพทย์

## C. เวลาแต่ละขั้นจากอุปกรณ์ในห้องผ่าตัด (กล้อง AI, RFID, ระบบในห้องผ่าตัด)

แทนการให้พยาบาลกดบันทึกเวลา: ระบบกล้อง AI แบบ ambient (เช่น Aimbient, Apella), เครื่องอ่าน RFID ที่ประตูห้อง (สายรัดข้อมือผู้ป่วย: ใช้ช่องทางเฉพาะในข้อ C.2) หรือระบบในห้องผ่าตัด ส่งเวลาแต่ละขั้นเข้ามาได้ทันที · API key สิทธิ์ `milestones:write` (แยก key ต่ออุปกรณ์/ระบบ)

```
POST /api/his/v1/milestones
Authorization: Bearer orc_…
Content-Type: application/json

{ "room": "OR-1", "step": "in_room", "time": "2026-11-23T08:05:12+07:00" }
```

| ช่อง | ความหมาย |
|---|---|
| `step` (บังคับ) | `arrived` มาถึงห้องเตรียม · `in_room` เข้าห้องผ่าตัด · `incision` ลงมีด · `closure` เย็บแผลเสร็จ · `out_room` ออกจากห้องผ่าตัด · `recovery_out` ออกจากห้องพักฟื้น |
| `room` | รหัสห้องผ่าตัด · **ส่งแค่ห้องได้** สำหรับ `in_room` (= เคสแรกของห้องที่ยังไม่เข้าห้อง) และ `incision` `closure` `out_room` (= เคสที่อยู่ในห้องตอนนี้) |
| `case_code` หรือ `his_ref` | ระบุเคสตรง ๆ (จำเป็นสำหรับ `arrived` และ `recovery_out`) · ส่งพร้อม `room` แล้วห้องไม่ตรง = ปฏิเสธ |
| `time` | ISO 8601 **พร้อมเขตเวลา** หรือ `HH:MM` (เวลาไทย) · ไม่ส่ง = เวลาที่ได้รับ |
| `date` | วันของตารางที่เคสอยู่ (ค่าตั้งต้น: วันของ `time` หรือวันนี้) · เคสข้ามเที่ยงคืน: ส่งวันที่เริ่มเคส |
| `replace` | `true` = แก้เวลาของขั้นที่บันทึกไว้แล้ว (ค่าตั้งต้น: ส่งซ้ำไม่เปลี่ยนอะไร ตอบ `UNCHANGED`) |

ตอบกลับ (ไม่มีข้อมูลผู้ป่วย):

```json
{ "status": "APPLIED", "case_code": "R-3F2A9C", "room": "OR-1", "step": "in_room", "step_label": "เข้าห้องผ่าตัด",
  "date": "2026-11-23", "time": "08:05", "stage": "อยู่ในห้องผ่าตัด" }
```

- **ตรวจเหมือนกดในหน้าเว็บ:** ขั้นต้องเรียงลำดับ ห้ามเวลาล่วงหน้า · ผิด = 400 พร้อมเหตุผล (เช่น "ตอนนี้ไม่มีเคสอยู่ในห้อง OR-1") · ไม่พบเคส = 404 · 401/403/429 เหมือนส่วน A
- เวลาเข้า–ออกห้องที่ได้ คือเวลาจริงที่รายงานผู้บริหาร การพยากรณ์เวลาผ่าตัด และ **โอกาสเกินเวลา** บนกระดานสถานะใช้ทันที · ผู้บันทึกแสดงเป็น "อุปกรณ์: <ชื่อ key>"
- **PDPA:** ภาพและเสียงอยู่ที่ระบบกล้องของโรงพยาบาล ORchestraAI รับเฉพาะเวลาและรหัสห้อง/เคส · การติดกล้องและไมโครโฟนในห้องผ่าตัดต้องมีความยินยอม การประเมินผลกระทบ (DPIA) และระยะเก็บภาพที่ชัดเจน

### C.2 สายรัดข้อมือ RFID (เครื่องอ่านที่ประตู · ไม่ต้องกดอะไร)

ติดแท็ก RFID ที่สายรัดข้อมือผู้ป่วย (เขียน **HN** ลงในแท็กตอนพิมพ์สายรัด) และติดเครื่องอ่านที่ประตูห้องผ่าตัด เข็นเปลผ่านประตูแล้วระบบบันทึกเวลาเอง ไม่ต้องหยุด ไม่ต้องเห็นหน้า · ใช้ key สิทธิ์ `milestones:write` เหมือนข้อ C (**แยก key ต่อเครื่องอ่าน** ตั้งชื่อเช่น "RFID ประตู OR-2" ผู้บันทึกจะแสดงเป็นชื่อนี้)

```
POST /api/his/v1/wristband
Authorization: Bearer orc_…
Content-Type: application/json

{ "tag": "65-0012345", "room": "OR-2", "time": "2026-11-23T08:04:31+07:00" }
```

| ช่อง | ความหมาย |
|---|---|
| `tag` (บังคับ) | ค่าที่อ่านได้จากสายรัด = HN ของผู้ป่วยตามที่อยู่ในใบขอผ่าตัด (ไม่สนช่องว่าง `-` `/` และตัวพิมพ์เล็ก/ใหญ่ แต่เลข 0 นำหน้าต้องตรงกัน) · ถ้าแท็กเก็บเป็นรหัสอื่น ให้ middleware ของเครื่องอ่านแปลงเป็น HN ก่อนส่ง |
| `room` | ห้องผ่าตัดที่ติดเครื่องอ่านไว้ที่ประตู · **ระบบแยกเองว่าเข้าหรือออก:** ผู้ป่วยยังไม่เข้าห้อง = `in_room` · อยู่ในห้องแล้ว = `out_room` |
| `step` | ระบุขั้นเองได้: เครื่องอ่าน 2 เสาที่รู้ทิศทาง (`in_room` / `out_room`) · เครื่องที่ห้องเตรียม (`arrived`, ไม่ต้องส่ง room) · เครื่องที่ทางออกห้องพักฟื้น (`recovery_out`) |
| `time`, `date` | เหมือนข้อ C · ไม่ส่ง `time` = เวลาที่ได้รับ |
| `dry_run` | `true` = ทดสอบเครื่องอ่าน: ตอบว่าจะบันทึกขั้นไหนของเคสไหน แต่ยังไม่บันทึกและไม่แจ้งเตือน |

ตอบกลับ (ไม่มี HN หรือข้อมูลผู้ป่วย) ด้วย HTTP 200 และ `status`:

| `status` | ความหมาย |
|---|---|
| `APPLIED` | บันทึกแล้ว (`case_code` `room` `step` `time` `stage`) |
| `DUPLICATE` | อ่านซ้ำในรอบเดียวกัน: ภายใน 10 นาทีจากเวลาที่ผู้ป่วยเข้าหรือออกห้องครั้งล่าสุด (เครื่องอ่านจับแท็กได้หลายครั้งตอนเข็นผ่าน) ไม่บันทึกซ้ำ |
| `UNCHANGED` | ขั้นนี้บันทึกไว้แล้ว (เช่น อ่านซ้ำที่ห้องเตรียม) |
| `IGNORED` | ผู้ป่วยไม่มีเคสที่รอเข้าหรืออยู่ในห้องผ่าตัดแล้ว (เช่น เข็นผ่านประตูหลังออกห้อง) |
| `WRONG_ROOM` | **เคสของผู้ป่วยนัดไว้อีกห้อง** (`room` = ห้องที่นัด, `reader_room` = ประตูที่อ่านได้) · ไม่บันทึกเวลา และ**แจ้งเตือนผู้ดูแลระบบและหัวหน้าพยาบาล** (เคสละครั้งต่อประตูใน 10 นาที · ข้อความมีแค่รหัสเคสและห้อง) · ถ้าย้ายห้องจริง ให้ย้ายเคสในตารางก่อน |
| `DRY_RUN` | ผลทดสอบ (`dry_run: true`) |

ไม่พบเคสของผู้ป่วยในวันนั้น = 404 (ข้อความไม่มี HN) · ขั้นที่บันทึกไม่ได้ (เช่น ออกจากห้องพักฟื้นก่อนออกจากห้องผ่าตัด) = 400 · ไม่ระบุทั้ง `room` และ `step` = 400

**การติดตั้ง:**
- ใช้เสาอากาศแบบ portal หันเข้าช่องประตู ปรับกำลังส่งให้อ่านได้เฉพาะตอนผ่านประตู ไม่อ่านเปลที่เข็นผ่านในทางเดิน (อ่านจากทางเดินจะทำให้เตือนผิดห้องโดยไม่จำเป็น)
- ตั้ง middleware ให้กรองการอ่านซ้ำ (ส่งครั้งเดียวต่อการผ่าน) และส่ง `time` เป็นเวลาที่อ่านได้จริง ถ้าเน็ตหลุดให้เก็บไว้ส่งทีหลัง (ระบบรับเวลาย้อนหลังได้)
- ทดสอบทีละประตูด้วย `dry_run: true` และสายรัดของเคสทดสอบ (ใช้ระบบฝึกซ้อม) ก่อนใช้จริง
- เวลาลงมีดและเย็บแผลเสร็จยังกดในหน้าเว็บ (หรือส่งจากระบบอื่นทางข้อ C)
- **PDPA:** ORchestraAI ใช้ HN จากแท็กเพื่อหาเคสเท่านั้น ไม่เก็บ ไม่ส่งกลับ และไม่ใส่ในบันทึกหรือการแจ้งเตือน · แท็ก RFID ไม่ใช่ข้อมูลชีวภาพ แต่ HN ในแท็กอ่านได้ด้วยเครื่องอ่านทั่วไป ควรเลือกแท็กที่ล็อกการเขียนได้ และทิ้งสายรัดตามขั้นตอนข้อมูลผู้ป่วยของโรงพยาบาล

## 2. ขั้นตอนเปิดใช้งาน

1. **ผู้ดูแล ORchestraAI:** หน้า ⚙ สถานะระบบ → รัน SQL ที่ยังขาด (ไฟล์ 017 และ 019)
2. **ทดลองด้วยไฟล์:** ข้อมูลโรงพยาบาล → เชื่อมต่อ HIS → นำเข้าไฟล์ FHIR → เลือก `docs/integration/sample-bundle.json` → ดูผลทดลอง (ยังไม่บันทึก)
3. **ขอไฟล์ Bundle ตัวอย่างจากฝ่าย IT** → ทดลองนำเข้า → ตั้งตารางจับคู่รหัส (ประเภทห้อง บทบาท ชนิดเครื่องมือ ประเภทเวร identifier system) จนไม่มีรายการ "ไม่ผ่าน" และรายการ "ข้าม" เป็นของที่ไม่ใช่ห้องผ่าตัดจริง ๆ → นำเข้าจริง
4. **เลือกทางรับข้อมูลประจำ:**
   - **HIS ส่งเข้ามา:** สร้าง API key สิทธิ์ "ส่งข้อมูลหลัก (FHIR)" → ส่ง key ให้ฝ่าย IT ทางช่องทางที่ปลอดภัย (ไม่ใช่แชตหรืออีเมล) → IT ตั้งให้ HIS / interface engine ส่ง Bundle เมื่อข้อมูลเปลี่ยน และส่งตารางเวรล่วงหน้าเป็นรอบ (เช่น ทุกคืน 2–4 สัปดาห์ข้างหน้า) → ทดลองด้วย `?dry_run=true` ก่อน
   - **ORchestraAI ไปดึง:** ใส่ที่อยู่ FHIR server และชื่อตัวแปร token → Railway → Variables เพิ่ม `HIS_TOKEN` → ทดสอบการเชื่อมต่อ → ดึงจาก HIS (ทดลอง) → ดึงจริง → ตั้งดึงอัตโนมัติ (เช่น ทุก 6 ชั่วโมง)
5. **ใบขอผ่าตัด (ส่วน B):** สร้าง key สิทธิ์ส่งใบขอผ่าตัด/อ่านตาราง → ping → ส่งใบขอทดสอบ → จับคู่รหัสที่ยังไม่รู้จัก → อ่านสถานะ → ยกเลิกใบทดสอบ
6. **เครื่องอ่าน RFID สายรัดข้อมือ (ส่วน C.2):** สร้าง key สิทธิ์ "ส่งเวลาแต่ละขั้นของเคส" แยกต่อเครื่องอ่าน → ทดสอบแต่ละประตูด้วย `dry_run` → ใช้จริง
7. ติดตามได้ที่ประวัติการรับข้อมูล (หน้าเชื่อมต่อ HIS) และหน้า ⚙ สถานะระบบ

## 3. ต่อยอดได้ (ยังไม่ทำ)

- ส่งตารางผ่าตัดกลับ HIS เป็น FHIR `Appointment` อัตโนมัติ (ตอนนี้ HIS อ่านจาก `GET /api/his/v1/schedule`)
- เตียงพักฟื้น (PACU / ICU) จาก `Location` physicalType `bd`
- ใบขอผ่าตัดเป็น FHIR `ServiceRequest` (ตอนนี้ใช้ JSON ส่วน B)
- เข้ารหัสเนื้อหาชั้นที่ 2 (JWE แบบ PhysioCare) เมื่อส่งข้อมูลผู้ป่วยผ่าน FHIR
- ยืนยันตัวแบบ SMART Backend Services (OAuth2 client credentials) หรือ mTLS แทน token / API key · FHIR Subscription แทนการดึงเป็นรอบ
